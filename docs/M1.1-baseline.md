## Diagnostic et correction de stockage

### Web / `vite/client`

`apps/web/tsconfig.json` demande les types `vite/client`, ce qui est la configuration attendue par Vite. `apps/web/package.json` déclare Vite et `@vitejs/plugin-react` en dépendances de développement; `package-lock.json` verrouille Vite `5.4.21` et le plugin React `4.7.0`. L’absence de type ne vient donc pas d’une déclaration manquante dans le manifeste ou d’un mauvais chemin `tsconfig`.

L’installation présente est incomplète : `npm ls --workspace @shortest/web --depth=0` ne trouve aucun paquet installé pour ce workspace, et `require.resolve` ne trouve ni Vite, ni son plugin, ni TanStack Router. Le verrou existe bien. `npm config get omit` ne signale pas d’exclusion de dépendances de développement. Aucun install n’a été lancé : il n’est pas justifié de modifier le lockfile pour corriger un `node_modules` manquant. Après restauration des paquets strictement depuis le verrou, relancer les contrôles web.

### Mobile / `localStorage`

Le contrat asynchrone `Storage` et les fonctions `loadSave`/`persistSave`/`resetSave` restent dans le moteur partagé. L’adaptateur navigateur a été déplacé dans `apps/web/src/storage.ts`; les deux clients web l’importent localement. L’adaptateur natif AsyncStorage reste dans `apps/mobile/src/storage.ts`. Les méthodes, la sérialisation JSON et les erreurs tolérées en lecture conservent le comportement précédent. `createGameStore` et l’interface `Storage` n’ont pas changé. L’ancien export `webStorage` est conservé comme shim de compatibilité déprécié, évalué seulement lorsqu’on appelle ses méthodes; les applications du monorepo n’en dépendent plus.

Résultat : le typecheck mobile passe sans ajouter les types DOM au `tsconfig` natif. Le code web continue d’utiliser l’adaptateur navigateur dédié.

## Commandes reproductibles

Depuis la racine du monorepo :

```sh
npm test
npm run typecheck -w @shortest/engine
npm run typecheck -w @shortest/web
npm run build -w @shortest/web
npm run typecheck -w @shortest/mobile
npm exec --workspace @shortest/mobile -- expo export --platform android --output-dir /tmp/mathprime-mobile-export
```

Après installation des dépendances depuis `package-lock.json`, les deux commandes web doivent être relancées. Pour une build Android native, installer/configurer Android command-line tools, SDK platform/build-tools correspondant aux versions Expo/Gradle du projet, puis utiliser Java 17 sélectionné par mise :

```sh
cd apps/mobile
mise exec -- ./android/gradlew -p android :app:assembleDebug --offline --no-daemon
```

## Prérequis M2 — Expo 54 → 58 et modernisation web

M1.1 n’a lancé aucune mise à niveau de dépendance. Préconditions pour M2 :

1. Restaurer `node_modules` depuis le lock et obtenir le typecheck/build web de référence. Depuis la racine, utiliser `npm ci` pour reproduire le lock existant, puis contrôler `git diff -- package-lock.json`. M1.1 ne l’a pas lancé car cette commande remplace l’arbre `node_modules` actuel; l’absence de paquets web suffisait à expliquer le blocage.
2. Maintenir une matrice de validation web sur les versions verrouillées avant de toucher aux dépendances. Vite `5.4.21` est dans les plages affectées des avis publiés; au minimum, sélectionner une version corrigée et maintenue compatible avec la version de `@vitejs/plugin-react`, puis tester le serveur de développement et le build de production. L’avis path traversal Vite indique un correctif dès `6.4.2`; les avis d’octobre 2026 fixent aussi la branche 6 à partir de `6.4.4`. Références : [GHSA-4w7w-66w2-5vf9](https://github.com/vitejs/vite/security/advisories/GHSA-4w7w-66w2-5vf9), [GHSA-rq7h-c2jc-7f22](https://github.com/vitejs/vite/security/advisories/GHSA-rq7h-c2jc-7f22).
3. SDK 58 est sorti le 15 octobre 2026 et inclut React Native 0.88 / React 19.3. Son outillage exige Node 22.13+ sur la branche 22, 24.3+ sur 24 ou Node 26+; Node 26.8.2 convient. La référence du SDK indique compile/target SDK Android 37/36; l’image EAS SDK 58 utilise JDK 17 et NDK r27b. Installer les command-line tools Android, platform 37, build-tools compatibles et NDK r27b; utiliser Java 17 via mise. Références : [notes SDK 58](https://expo.dev/changelog/sdk-58), [référence SDK 58](https://docs.expo.dev/versions/v58.0.0/), [image de build SDK 58](https://docs.expo.dev/build-reference/infrastructure/).
4. Migrer SDK par SDK (54 → 55 → 56 → 57 → 58), en examinant les changelogs, les versions Expo compatibles et les différences du projet natif Android à chaque étape. Le dossier `apps/mobile/android` et son keystore debug restent en place; aucune régénération destructive n’est prévue. Appliquer les changements nécessaires avec le Native Project Upgrade Helper et revoir le diff Gradle/manifest/ressources.
5. Choisir explicitement si iOS fait partie de la release. Les notes SDK 58 décrivent le cycle de vie UIKit requis par iOS 27; la référence SDK indique iOS 16.4+ et Xcode 26.4+. Le dépôt n’a pas de projet iOS natif. Si iOS est retenu, établir un environnement macOS/Xcode et une stratégie de génération/maintenance avant de migrer.
6. Avant toute release, isoler une signature de production et ses secrets de la signature debug actuelle. Ne pas supprimer le keystore debug pendant cette étape.
7. À chaque palier Expo, relancer tests, typechecks, export Metro et build Android natif. Exécuter Expo Doctor lorsque l’environnement réseau et les outils Android sont disponibles.
