# MathPrime — R2.1 : playtest terminal Rogue V1

Prototype expérimental construit depuis `modernization` (`08e58f7`, fusion de la PR #8), sur `feat/rogue-v1-playtest`. Aucune intégration dans les écrans web ou mobile, aucun changement Classic, Big Challenge, Free Skill, Daily, Supabase ou classement. Aucun paramètre d'équilibrage R1.1 n'est modifié.

## Lancer une partie

Depuis la racine, avec les dépendances du projet installées :

```sh
npm run playtest:rogue-v1 -w @shortest/engine
npm run playtest:rogue-v1 -w @shortest/engine -- --format short --seed 42
npm run playtest:rogue-v1 -w @shortest/engine -- --format full --seed 123
npm run playtest:rogue-v1 -w @shortest/engine -- --help
```

Utilise Node et le chargeur `tsx` déjà présents dans le projet ; aucune nouvelle dépendance. La CLI est en français. Graine entière non signée de 0 à 4 294 967 295 ; valeur par défaut 42. Options inconnues ou incomplètes refusées avant création d'une session.

- **full**, format par défaut : trois actes, trois boss, 16 réussites pour la victoire officielle. Choix explicite de terminer ou continuer en survie.
- **short** : les trois puzzles ordinaires de l'acte I, son choix tactique et les deux phases du Gardien du rythme. Arrêt après le bilan du boss I, avant le draft majeur. Cinq réussites requises ; aucun score de victoire complète attribué. Format identifié par `format: "short"` et issue `short-completed` dans le rapport.

Le test court utilise les mêmes règles, temps et ressources que le début d'une run complète ; seul son point d'arrêt change. Une graine reproduit les puzzles à décisions de cartes et résultats identiques ; des choix, échecs ou chronomètres différents changent la suite du parcours.

## Commandes et déroulement

| Commande | Action |
| --- | --- |
| `aide` | Afficher les commandes et la syntaxe |
| `demarrer` | Lancer le puzzle préparé et son chronomètre |
| `soumettre 3+5*7` | Soumettre une réponse définitive, avec perte de vie possible |
| `indice` | Consommer un indice et recevoir une indication partielle |
| `effets` | Consulter les effets actifs, leur niveau, avantage, contrepartie et durée |
| `temps` | Afficher le temps restant sans arrêter le chronomètre |
| `suivant` | Quitter le résultat et passer à la préparation ou à une récompense |
| `choisir 1`, `choisir 2`, `choisir 3` | Prendre l'offre numérotée |
| `choisir 0` | Refuser toutes les offres, y compris un draft vide |
| `terminer` | Terminer après la victoire officielle |
| `survie` | Continuer après la victoire officielle |
| `quitter` | Abandonner proprement et enregistrer le rapport |

Seuls les chiffres isolés sont acceptés syntaxiquement ; répétitions permises. `*` ou `×` pour la multiplication, `-` ou `−` pour la soustraction ; espaces tolérés, pas de parenthèses. Priorités opératoires habituelles. Une expression seule, une commande inconnue ou une syntaxe incomplète ne soumet rien et ne retire aucune vie. Le temps continue malgré ces erreurs. Une réponse syntaxiquement valide explicitement soumise avec une mauvaise valeur, un chiffre interdit ou une contrainte non respectée est un échec terminal.

Avant chaque tentative, la préparation montre la cible, l'acte, l'avancement, les chiffres 3/5/7, les opérations, les obligations exactes et le temps alloué. Le minimum du solveur et le témoin sont cachés jusqu'au résultat. Les introductions des trois boss décrivent leurs mécaniques ; les phases de l'Architecte annoncent leur précision minimale avant `demarrer`.

Après chaque tentative : réponse et valeur calculée, résultat/cause, étoiles, minimum dans les bornes, témoin, points (bonus de boss inclus), vies perdues et restantes, indices consommés, effets expirés/actualisés, bonus ou malus de temps différé. Une assurance consommée est visible dans les effets. La dernière défaite reste un résultat à lire avant `suivant` ; quitter à cet écran conserve la cause de défaite.

Les drafts sont marqués TACTIQUE ou MAJEURE. Chaque offre affiche son avantage, sa contrepartie et sa durée. Les termes des améliorations utilisent bien le niveau supérieur réellement appliqué. Un remplacement affiche exactement l'identifiant et le nom sacrifiés : le prototype conserve le choix automatique R1 du premier durable et ne prétend pas proposer un choix libre de sacrifice.

## Chronomètre et séparation du moteur

Le moteur reste piloté par `advance` et sans timers réels. Le contrôleur `src/rogue-v1/playtest/session.ts` reçoit une interface `Clock` (`now`, `schedule`, `cancel`). L'adaptateur `scripts/playtest-rogue-v1.ts` utilise `performance.now()` pour le temps monotone, et `setTimeout` pour l'expiration automatique. Un intervalle d'affichage d'une seconde n'affecte pas la logique du moteur.

La cible et les règles sont générées en préparation ; aucun temps de recherche ni d'attente de préparation n'est facturé. `demarrer` commence le temps. Saisie, aide, effets et indices ne le suspendent pas. Chaque commande synchronise d'abord le temps écoulé ; si la limite est déjà atteinte, le timeout gagne sur la réponse arrivée trop tard. Le callback d'expiration synchronise le même état, même sans saisie. Annulation du timer et numéro de génération empêchent les callbacks périmés de retirer une seconde vie ou de toucher une nouvelle tentative.

Aucun timer pendant résultats, récompenses, préparation, choix victoire/survie ou session terminée. Le temps total de session inclut ces attentes ; le temps par tentative compte seulement le jeu. La latence du terminal et de l'écriture locale fait partie du temps réel pendant le jeu ; ce prototype n'est pas un chronomètre compétitif.

Dans un terminal ANSI, le compte à rebours met à jour l'invite readline en préservant la ligne et le curseur de saisie. À expiration, la saisie non soumise est effacée avant le résultat. Dans `TERM=dumb`, un pipe ou une sortie non interactive, le rafraîchissement est désactivé pour ne pas accumuler d'invites ; `temps` permet de consulter le restant et l'expiration reste automatique. Dans ce mode dégradé, une ligne partiellement tapée peut devoir être vidée par Entrée avant la commande suivante ; elle ne devient jamais une réponse sans `soumettre` et le bon écran.

EOF, Ctrl-D, Ctrl-C en terminal interactif et SIGTERM terminent proprement la session. SIGKILL, panne ou fermeture brutale ne peuvent pas garantir la sauvegarde finale : le dernier autosave reste exploitable avec son issue `in-progress`.

## Indices progressifs

Le placeholder révélant le témoin entier a été retiré de l'API expérimentale R1. Les trois demandes possibles sur un même puzzle donnent successivement :

1. Le nombre de multiplications d'une solution valide.
2. Le nombre exact d'occurrences du chiffre 7 dans cette solution.
3. Le nombre de soustractions dans cette solution.

Ces faits viennent du même témoin valide sous les contraintes réellement actives. Ils ne promettent pas que toutes les solutions ont ces propriétés, et ne montrent aucune expression complète. Les informations ne se répètent pas sur une même tentative ; un puzzle recommencé possède de nouvelles indications. Sur une petite cible, ces faits peuvent permettre de déduire rapidement une solution : leur utilité et leur puissance restent à évaluer.

Réserve globale de trois indices ; un consommé par demande ; pénalité linéaire de 15 % par indice dans la formule R1, sans plafond d'étoiles. Consulter un indice laisse le temps passer. Les configurations arbitraires avec plus de trois demandes sur un même puzzle ne sont pas prises en charge par cette première progression ; l'API refuse une quatrième information sans consommer de ressource. La CLI conserve la réserve standard de trois et n'expose pas de réglage pour la dépasser.

## Journaux locaux et confidentialité

Emplacement fixe, indépendant du répertoire courant : **`.playtests/rogue-v1/` à la racine du dépôt**. Un nom UTC avec UUID évite les collisions. Chaque session est un JSON distinct, chemin affiché à la fin. Le dossier est exclu de Git et aucune session personnelle n'est incluse dans les commits. L'écriture est faite par fichier temporaire dans le même dossier puis renommage ; permissions du nouveau fichier limitées au propriétaire (0600).

Autosave à la préparation initiale, après chaque commande et sur expiration, puis rapport final après fin ou abandon. Une erreur d'écriture est signalée, arrête la session et donne un code de sortie d'échec : elle ne simule pas un journal réussi.

Champs principaux :

- `schemaVersion`, `engineVersion` (identifiant R2.1 du prototype), configuration R1, graine initiale, format et durée totale.
- `attempts` : puzzle, contraintes, variante de boss, candidats admissibles, diagnostics D1/T3 et avertissements, effets avant/après, temps réellement consacré, réponse et valeur, étoiles, points, indices reçus, pertes de vies, cause et résultat.
- `events` : événements du moteur, drafts proposés, refus et choix réels, ressources, effets, récompenses de boss et victoire officielle.
- `bossReached` (boss proposés en préparation), `defeatedBosses`, score, vies, indices finaux, `officialVictory` et issue : `victory-finished`, échec terminal, `abandoned`, `short-completed`, `generation-unavailable` ou `in-progress`.

Le témoin est masqué aussi dans l'autosave de la tentative en cours (`witnessWithheld`), y compris son événement de génération. Il devient disponible après le résultat ou la clôture pour l'analyse. Les commandes invalides et les textes libres ne sont pas conservés ; seules les expressions mathématiques définitivement soumises et les décisions utiles sont enregistrées. Aucun nom, courriel, profil utilisateur ou identifiant de machine n'est demandé. Aucun envoi réseau, Supabase, télémétrie ou classement. Pas de CSV à cette étape : le JSON préserve les contraintes et les effets imbriqués.

Une victoire officielle reste vraie après défaite ou abandon en survie. Le résultat final et le score de survie doivent être analysés séparément d'une victoire arrêtée au boss final. Un test court terminé n'est pas une victoire de run complète.

## Implémentation et contrôles

- `hints.ts` : indications partielles, utilisées par `run.ts`, sans modification des coûts ou du score.
- `playtest/session.ts` : contrôleur sans entrée/sortie système, préparation, horloge injectée, commandes et rapports.
- `playtest/render.ts` : présentation terminal et descriptions exactes des cartes/niveaux.
- `playtest/options.ts` : validation des options sans démarrer de session.
- `scripts/playtest-rogue-v1.ts` : readline, horloge monotone, affichage, signaux et cycle de vie.
- `scripts/rogue-playtest-log.ts` : écriture locale atomique.
- `tsconfig.playtest.json` : vérification TypeScript de l'adaptateur Node en plus des contrôles moteur existants.

Vérifications exécutées :

```sh
npm test
npm run typecheck -w @shortest/engine
npm run typecheck -w @shortest/web
npm run typecheck -w @shortest/mobile
npm run build -w @shortest/web
git diff --check
git check-ignore .playtests/rogue-v1/example.json
```

**86 tests réussis** : les 76 groupes R1/R1.1 et dix nouveaux groupes R2.1. Tests sans longue attente : horloge manuelle, expiration sans saisie, double callback/stale callback, concurrence timeout/réponse, préparation et attentes, erreurs de commande, indices et pénalité sans plafond d'étoiles, affichage des obligations, cartes, format court, trois boss et victoire complète, finition ou défaite en survie, abandon et aller-retour d'un JSON dans un dossier temporaire nettoyé. Aucune sous-exécution Node n'est nécessaire pour ces assertions.

Typechecks moteur (avec adaptateur Node), web, mobile et build web réussis. Aucun résultat de CI distante n'est affirmé avant publication de la branche.

Essai manuel dans un pseudo-terminal Linux : lancement via npm, deux réponses réussies dont une à deux étoiles, indice partiel, draft tactique et T3 appliqué, expiration automatique avec ligne partiellement saisie, vie perdue une seule fois et abandon avec JSON local. Second essai ANSI : compte à rebours conservant une expression partielle puis complétion et soumission réussie en environ 8 s. Mode non interactif testé par `quitter` dans un pipe. Ces essais sont des contrôles techniques de l'agent, **pas des résultats humains d'équilibrage**. Le parcours complet et la survie ont été exercés automatiquement via le contrôleur et l'horloge simulée, pas manuellement sur une partie humaine complète.

Problèmes rencontrés et corrigés : invites répétées dans `TERM=dumb` (mode sans rafraîchissement), saisie périmée au timeout ANSI (effacée), timeout arrivé avant une commande quitter (clôture garantie), indices dévoilant le témoin R1 (remplacés). Les tests de parsing utilisent la fonction pure, car l'environnement restreint refuse les sous-processus lancés depuis Node ; la commande réelle a été exécutée séparément dans le terminal.

## Limites et recommandations pour R2.2

R2.1 fournit l'outil de collecte, sans prétendre que le jeu est équilibré. D1/T3 parfois peu restrictifs, pools étroits, coût heuristique non calibré et avertissements temporels R1.1 sont conservés et journalisés. Un avertissement temporel n'annule ni le témoin ni le minimum borné : solvabilité, optimalité dans les bornes et jouabilité humaine sont trois informations distinctes.

Premiers playtests : commencer par un test court, expliquer explicitement `soumettre`, laisser lire les obligations avant démarrage, puis proposer une run complète. Recueillir séparément des commentaires volontaires sur les indices, contraintes difficiles et pression temporelle ; le JSON ne recueille pas de texte personnel. Éviter d'ouvrir les rapports pendant une session si l'on veut tester sans connaissance des tentatives antérieures. Comparer des sessions de même format et analyser les échecs par cause, les temps avec/sans indice, les offres refusées et la diversité des cibles.

R2.2 pourra examiner l'aide réellement utile, la répétition des cibles dans les pools étroits, les obligations déjà satisfaites, la difficulté humaine et le besoin d'un remplacement librement choisi. Les multiplicateurs et temps doivent attendre ces observations. Restent hors périmètre : maquettes, interface graphique, intégration production, serveur de télémétrie, anti-triche, benchmark Android et diffusion des journaux.
