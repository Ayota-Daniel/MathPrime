# M2.1 — Modernisation du web

## Baseline avant modernisation Vite

Branche : `chore/m2-web`, créée depuis `modernization` (`2a5dfb3`). Les commits M1 (`c63009c`) et M1.1 (`2a5dfb3`) sont dans l'historique. Le tag `legacy-v1` pointe toujours vers `df5f749`. Les refs GitHub `modernization` et `legacy-v1` correspondaient déjà à ces références ; aucun commit ni tag ne manquait sur `origin`.

Environnement observé : Node `v26.8.2`, npm `11.19.1`; workspaces npm `packages/*` et `apps/*`. `npm ci` a restauré 744 paquets sans modifier le lockfile. Le premier essai a échoué sur une erreur DNS temporaire vers `registry.npmjs.org`; le second a réussi.

La première baseline après installation a donné 16/16 tests, typecheck moteur et typecheck mobile réussis. Le typecheck web et le build échouaient sur les composants JSX avec des `ReactNode` incompatibles. La cause était la résolution partagée de React 19.1/types 19 du workspace Expo/mobile avec React 18.3/types 18 déclarés par le web. Le correctif minimal retenu est d'aligner les dépendances React du web sur React 19.1 et les types React 19, version déjà employée par Expo SDK 54. Aucun code produit ni comportement du jeu n'a changé.

Après cet alignement, avant la mise à jour de Vite :

| `npm run typecheck -w @shortest/engine` | Réussi |

Le build de référence a généré `apps/web/dist` (1747 modules, bundle JS 353.55 kB / 112.44 kB gzip). npm a signalé des dépendances dépréciées et des scripts postinstall esbuild non explicitement approuvés dans sa configuration locale. L'audit npm initial n'a pas pu joindre son endpoint de sécurité; le bilan final doit utiliser un audit réussi ou indiquer cette limite.

## Modernisation web

### Versions et décisions

| Dépendance | Avant | Après |

| TanStack Query | 5.104.4 | 5.105.0 |

| `postcss-selector-parser` transitif | 6.1.4 | 6.1.5 |
| TypeScript / Tailwind | 5.9.3 / 3.4.19 | inchangés |

Vite 7.3.7 a été retenu parmi Vite 7.3 et 8.3. Les deux branches ont une version stable récente et acceptent la version de Node locale (26.8.2). Vite 8.3.5 introduit Rolldown et Oxc à la place de Rollup et esbuild; le plugin React 6 associé a abandonné ses options Babel. Cette application n'a pas besoin de cette nouvelle chaîne. Vite 7.3.7 conserve le moteur de build précédent, reste dans la branche antérieure maintenue et inclut les correctifs de sécurité publiés en octobre 2026. Le plugin React 5.2.0 a été vérifié compatible avec Vite 7. TanStack Router reste utilisé; Query et Router ont reçu leurs mises à jour stables non majeures. [Politique de support Vite](https://vite.dev/guide/releases), [migration Vite 8](https://vite.dev/guide/migration.html), [changelog plugin React](https://github.com/vitejs/vite-plugin-react/blob/main/packages/plugin-react/CHANGELOG.md).

React web a été aligné sur React 19.1.0 parce que le workspace mobile Expo 54 le résout déjà à la racine. La configuration précédente mélangeait React 18/types 18 côté web avec React 19/types 19 des paquets partagés, et le typecheck rejetait les composants JSX avec des `ReactNode` incompatibles. Les typechecks web/mobile et le build ont confirmé l'alignement. Le runtime React Native et Expo n'a pas été modifié. [React 19 est stable](https://react.dev/blog/2024/12/05/react-19).

Le moteur a 16 tests réussis, 0 échec. Cela couvre notamment précédence, minimum dans les bornes testées, Big Challenge, contraintes, scoring/progression et la reproductibilité des tables par le générateur. Les six tests marqués `BUG CARACTÉRISÉ` continuent de reproduire Rogue incompatible/insoluble, score Rogue doublé, premier envoi leaderboard bloqué, Daily rejouable et validation permissive; ces défauts n'ont pas été modifiés.

Le build Vite 7.3.7 a transformé 1740 modules et produit un JS de 340.20 kB (110.08 kB gzip), contre 1747 modules et 353.55 kB (112.44 kB gzip) avec Vite 5.4.21 après le correctif baseline React. Les quatre JSON de puzzles sont inchangés dans Git; le test moteur confirme leur format et leur reproductibilité. Le serveur Vite a démarré à nouveau après `npm ci`. Vérification interactive dans le navigateur : `/`, `/settings`, `/about`, `/stats`, `/leaderboard` et `/play/classic`, `/play/big3`, `/play/big5`, `/play/big7`, `/play/daily`, `/play/freeskill`, `/play/rogue` ont rendu leur écran et une cible. Les tables chargées par les routes affichaient aussi le compte optimal. Aucun message console d'erreur. Le leaderboard affichait `local`; l'opt-in et le pseudo de test ont persisté après rechargement.

La vérification de persistance n'a pas soumis de score. Le parcours d'envoi de record est déjà connu comme bloqué par le bug caractérisé M1 et n'a pas été corrigé à cette étape. Aucune authentification ni persistance distante Supabase n'a été testée; ces parcours nécessitent des identifiants/configuration et ne sont pas présumés opérationnels.

`npm ci` signale toujours des paquets dépréciés (`inflight`, `rimraf@3`, `glob@7`, `uuid@7`) et un script d'installation esbuild non approuvé par la configuration npm locale. Le build, le serveur et les typechecks réussissent malgré cet avertissement.

### Sécurité

Au 31 octobre 2026, `npm audit --workspace @shortest/web` rapporte **0 vulnérabilité** après l'override de `postcss-selector-parser` 6.1.5. L'audit du monorepo complet compte **31 entrées** : 3 high, 27 moderate et 1 low, toutes dans des dépendances Expo/React Native hors bundle web. Aucune vulnérabilité critique. Aucun `npm audit fix --force` n'a été exécuté.

Les trois alertes high sont des risques conditionnels dans l'outillage SDK 54 : `image-size` via Metro peut boucler sur certaines images JXL/HEIF/ICNS malveillantes; `node-forge` est utilisé par Expo CLI et ses outils de certificats; PostCSS 8.4.49 est imbriqué sous `@expo/metro-config` et ses alertes de lecture de fichiers demandent un CSS/source map contrôlé par un attaquant. Elles ne sont pas dans les dépendances web résolues ni dans le bundle web. Les avis glob/minimatch et les autres alertes modérées/low relèvent aussi de la chaîne locale Expo/RN, généralement lorsqu'elle traite des entrées/configurations non fiables. Leur exposition effective dépend de l'usage des commandes natives avec des entrées hostiles; cela doit être réévalué pendant M2.2, sans appliquer des overrides globaux à l'aveugle. Avis détaillés : [image-size HEIF/JXL](https://github.com/advisories/GHSA-5p2g-fcmc-qvqq), [image-size ICNS](https://github.com/advisories/GHSA-w3rx-r6r6-pgpr), [node-forge](https://github.com/advisories/GHSA-5x38-2vff-x55p), [PostCSS](https://github.com/advisories/GHSA-r28c-9q8g-f849).

### Régressions et limites

Aucune régression observée dans les contrôles exécutés. Le rendu a été vérifié sur les routes de développement; aucun test navigateur automatisé reproductible n'a été ajouté. Le build de production a réussi. Le push Git SSH n'a pas été possible depuis l'environnement : après contournement de la configuration SSH locale mal formée, GitHub a refusé l'accès faute de clé publique (`Permission denied (publickey)`). La référence distante `modernization` avait été vérifiée et pointait sur `2a5dfb3`; la PR et la publication de la branche restent à finaliser via le connecteur GitHub si son écriture est disponible.

### Préparation M2.2 — Expo SDK 54 → 58

SDK 58 associe React Native 0.88 et React 19.3, exige Node 22.13+ sur la branche 22, 24.3+ sur 24 ou Node 26+, et utilise Android compile SDK 37 / target SDK 36, Java 17 et NDK 27.1.12297006 sur l'image EAS SDK 58. Node local 26.8.2 satisfait l'exigence. [Référence SDK 58](https://docs.expo.dev/versions/v58.0.0/), [changelog SDK 58](https://expo.dev/changelog/sdk-58), [images EAS](https://docs.expo.dev/build-reference/infrastructure/).

Avant M2.2, inventorier les versions Expo recommandées par SDK 58 pour chaque module natif, vérifier le JDK/SDK/NDK et le keystore debug existants, examiner les modifications entre SDK 54 et 58 du dossier `android/`, puis préparer les adaptations natives et tester un build Android debug. La migration doit suivre les changements RN 0.87/0.88, dont la nouvelle API TypeScript stricte, et traiter explicitement les avis npm restants. Le dossier Android natif et son keystore debug sont conservés; les instructions Expo de suppression/régénération ne s'appliquent qu'aux projets générés avec Continuous Native Generation. M2.2 ne commence qu'après validation de M2.1.
