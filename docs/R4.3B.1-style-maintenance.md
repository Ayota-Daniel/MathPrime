# Rogue — Reprise manuelle des styles

Proposition progressive R4.3B.1. Conserver Tailwind 3 et NativeWind 4 installés ; aucune mise à niveau ni bibliothèque de composants supplémentaire dans ce correctif.

## Ce qui est déjà amorcé sur Web

Les couleurs restent dans `packages/tokens/index.ts`, export `rogue`. `screens/Rogue.tsx` les expose en variables `--r-*` sur la seule racine Rogue. Ce fichier ne nécessite pas de changement : le défaut venait du contexte hérité des panneaux, pas de l’injection des tokens.

`rogue.css` définit deux contextes : accueil clair et `.rogue-dark-surface`. Le second redéfinit **ensemble** surface, texte principal, texte secondaire, bordure et focus. Il s’applique à un panneau sombre même si son parent est l’accueil ivoire.

Les nouveaux noms de `apps/web/tailwind.config.js` utilisent ces rôles, sans dupliquer les hexadécimaux :

| Classe | Rôle / variable |
|---|---|
| `bg-rogue-surface` | `--surface` |
| `text-rogue-ink` | `--ink` |
| `text-rogue-muted` | `--secondary` |
| `border-rogue-line` | `--line` |
| `rounded-rogue-panel` | `rogue.radius.panel` partagé |

L’historique utilise les classes Tailwind sémantiques réunies dans `darkPanelClasses`. Depuis la reprise visuelle, le didacticiel emploie le contexte clair de l’accueil et ses règles locales `.rogue-lesson`. Les panneaux de partie utilisent le contexte sombre. La composition du plateau se trouve dans `.rogue-entry-live`, les repères de progression dans `RogueProgress.tsx` et les offres dans `RogueCards.tsx`.

Exemple du contexte déjà utilisable :

```tsx
<section
  className="rogue-dark-surface rounded-rogue-panel border border-rogue-line bg-rogue-surface p-7 text-rogue-ink"
>
  <h2>Un titre lisible</h2>
  <p className="text-rogue-muted">Une information secondaire</p>
</section>
```

Pour un autre panneau sombre, reprendre ce contexte complet. Ajouter seulement `bg-rogue-surface` sur un parent clair ne garantit pas une couleur de texte appropriée. Ne pas utiliser pour l’instant de suffixe d’opacité tel que `text-rogue-ink/50` : ces couleurs sont des variables hexadécimales, sans contrat RGB avec alpha.

## Lots Web suivants

1. **Un composant à la fois.** Continuer par les petits blocs de build/cartes, puis les conteneurs de préparation/résultat. Déplacer padding, grille, alignements et couleurs dans les classes du composant ; enlever uniquement les mêmes déclarations CSS devenues inutiles dans ce lot. Capturer le même état avant/après.
2. **Contrôles Rogue.** Traiter ensuite boutons et touches avec des variantes explicites, en conservant leurs événements, sons et attributs d’accessibilité. Les composants globaux `components/ui.tsx` sont aussi utilisés par les autres modes : leurs styles restent inchangés. Ne pas superposer de nouvelles classes à `.rogue-web button` en supposant qu’elles gagneront : ce sélecteur peut avoir une priorité supérieure. Retirer la règle concurrente lorsque son composant a réellement migré.
3. **Composition du puzzle en dernier.** Migrer ses colonnes, puis son responsive et bandeau fixe, sans déplacer la logique du contrôleur. Vérifier au moins un champ vide, un calcul, une erreur et une offre. Deux puzzles suffisent pour atteindre le premier choix ; aucune raison de rejouer toute une run pour les couleurs.

Conserver en CSS les `@font-face`, les contextes de variables, les pseudo-éléments du chronomètre et les cas navigateur spécifiques. Les microtransitions et la réduction de mouvement peuvent rester dans cette feuille. Les anciennes couleurs des autres modes ne sont pas renommées.

Le pavé Rogue utilise le bouton sonore partagé et les classes locales `.rogue-digit` et `.rogue-operator`. La couleur inline de `Tile` concernait l’ancien pavé. La feuille Rogue réserve désormais `!important` à la réduction de mouvement.

Les classes conditionnelles doivent être des chaînes complètes : par exemple `selected ? "border-rogue-line" : "border-transparent"`, pas `"border-" + role`. Le générateur Tailwind cherche les noms présents dans les sources. [Configuration du thème](https://v3.tailwindcss.com/docs/theme), [détection des classes](https://v3.tailwindcss.com/docs/content-configuration#dynamic-class-names).

## État Android vérifié dans le dépôt

`apps/mobile/tailwind.config.js` utilise déjà `nativewind/preset`. Metro passe par `withNativeWind` et `global.css` ; Babel inclut l’interop NativeWind. Les composants globaux emploient `className`.

Rogue utilise actuellement `StyleSheet` dans `rogue/styles.ts`, `rogue/ui.tsx` et `rogue/RogueInput.tsx`, plus des tableaux de styles pour les états et la hauteur de fenêtre. Ce choix a notamment corrigé une incompatibilité observée avec les fonctions de style Pressable pendant R4.3B. La présence de NativeWind dans le projet ne prouve pas que chaque conversion Rogue est déjà testée sur Android.

**Aucun code/configuration natif n’est modifié dans R4.3B.1.** Proposition pour un futur lot natif :

1. Ajouter un espace de noms de couleurs `rogue` depuis `rogue.colors` dans le thème NativeWind, des rayons dédiés et des familles `rogue-body`, `rogue-strong`, `rogue-display` pointant vers les noms chargés par Expo Font. Garder les tokens existants.
2. Convertir une rangée statique et un texte secondaire d’un écran non chronométré. Exemples :

```tsx
<View className="flex-row gap-[6px]">
  <Text className="font-rogue-strong text-[14px] text-rogue-ivory">
    Votre build
  </Text>
</View>
```

Ces classes de thème natives sont une **proposition**, pas des classes déjà disponibles dans le correctif. Définir les couleurs sur les `Text` ; ne pas supposer l’héritage Web à travers un `View`.

3. Étendre aux surfaces et labels statiques. Utiliser des valeurs explicites quand il faut conserver des dp : `gap-[6px]`, `p-[20px]`, `min-h-[44px]`. Ne pas remplacer mécaniquement ces nombres par l’échelle Web : la configuration installée convertit par défaut le rem natif à 14, contre 16 px usuels sur Web. [Unités NativeWind](https://www.nativewind.dev/docs/core-concepts/units).
4. Laisser les styles dynamiques dans les tableaux `style`, avec un propriétaire clair pour chaque propriété : adaptation à la hauteur, sélection, calculs de taille et états qui exigent une valeur calculée. Conserver les particularités natives : ripple, Safe Areas, Modal, TextInput, focus/sélection contrôlés et protections Fabric. [Priorité des styles NativeWind](https://www.nativewind.dev/docs/core-concepts/style-specificity).

Le champ et le pavé viennent en dernier. Ne modifier ni `showSoftInputOnFocus={false}`, ni le rejet d’éditions externes, ni `collapsable={false}`, ni la gestion des événements. Un changement natif réel nécessitera alors un build et un essai ciblé sur émulateur ; un typecheck seul ne valide pas l’interop.

## Petite procédure de maintenance

Pour chaque lot : choisir un propriétaire des styles, garder une capture de l’état initial, migrer un seul bloc, supprimer son ancien style concurrent, puis examiner son rendu. Vérifier le texte principal, le texte secondaire, le placeholder, une valeur saisie, une erreur, les états disponibles/désactivés et le focus clavier sur les **fonds réellement présents**.

Cible : au moins 4,5:1 pour le texte ordinaire. Les contrôles inactifs sont exemptés par WCAG 1.4.3, mais ce correctif vise aussi leur lisibilité. Mesurer la couleur calculée, le fond des ancêtres et l’opacité composée ; ne pas tester seulement deux tokens isolés. [Critère W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

Exécuter les tests/typechecks concernés et le build Web si ses styles changent, puis `git diff --check` et la vérification de confidentialité. Revenir à la capture du lot si une régression apparaît. Toute décision de proportions, typographie artistique, illustrations ou nouvelle composition attend la revue utilisateur ; ce plan ne vaut pas validation visuelle.

## Écrans communs de MathPrime

| Modification souhaitée | Point d’entrée |
|---|---|
| Couleurs, libellés de modes et polices | `packages/tokens/index.ts`. Les deux configurations Tailwind y lisent la palette. |
| Filigranes | Les quatre textures sont dans `packages/tokens/assets/backgrounds/`. Le Web choisit le format dans `apps/web/src/index.css` et complète le coin libre du papier paysage. Android compose son fond dans `GameScreen.tsx`. Les écrans de puzzle réutilisent le fond du conteneur. |
| Pavé et bouton principal | `components/ui.tsx` de chaque application pour Classic, Daily, Big Challenge et Free Skill. Rogue conserve ses commandes de sélection et son propre composant `rogue/ui.tsx` sur Android. |
| Migration suivante | Commencer par les cartes de statistiques et les lignes des paramètres. Convertir les marges, couleurs et alignements d’un seul composant à la fois. Comparer avec la capture correspondante avant de passer au suivant. |

Sur le Web, garder les compositions responsive, les pseudo-éléments de filigrane et les états de focus en CSS. Sur Android, garder le fond absolu, les Safe Areas, les largeurs calculées et les traitements de sélection dans les styles natifs. Les deux interfaces utilisent les mêmes valeurs de progression du moteur.
