# M2.3 — Première CI GitHub Actions

## Pourquoi une CI ?

Une intégration continue (CI) relance automatiquement les vérifications du projet quand on propose ou pousse un changement. Elle permet de repérer un test cassé, une erreur TypeScript ou un build web en échec avant la fusion.

Le workflow de MathPrime s'exécute pour les Pull Requests et les pushs vers `modernization` et `main`. Il installe les dépendances depuis le lockfile, lance les 16 tests du moteur, vérifie les types des trois workspaces, puis construit le web.

## Les mots utilisés

- Un **workflow** est le fichier qui décrit l'automatisation. Ici, c'est `.github/workflows/ci.yml`.
- Un **event** est l'événement qui démarre le workflow. `pull_request` et `push` en sont les deux événements configurés.
- Un **job** est un ensemble d'étapes exécutées sur un même environnement. Ce workflow contient le job `CI monorepo`.
- Un **runner** est la machine temporaire qui exécute le job. `ubuntu-latest` demande une machine Ubuntu hébergée par GitHub.
- Une **step** (étape) est une action ou une commande du job. Les étapes s'exécutent dans l'ordre écrit; si une étape échoue, les suivantes sont arrêtées.

`actions/checkout@v7` récupère le code. `actions/setup-node@v7` installe Node.js 26 et met en cache les données npm d'après `package-lock.json`. Au moment de la préparation, les dernières versions stables publiées étaient checkout 7.0.1 et setup-node 7.1.0; le workflow utilise leurs tags majeurs `v7`, que les éditeurs mettent à jour avec les correctifs compatibles. Sources officielles : [releases checkout](https://github.com/actions/checkout/releases) et [releases setup-node](https://github.com/actions/setup-node/releases). La version précise de Node dans le workflow est `26`.

Les commandes utilisent les noms de workspaces npm tels qu'ils apparaissent dans leurs `package.json`. Le cache n'inclut pas `node_modules` : `npm ci` reconstruit celui-ci depuis le lockfile. La permission du jeton du job est limitée à `contents: read`, ce qui suffit pour télécharger le dépôt et installer ses dépendances. Le job s'arrête au bout de 20 minutes. Le build Android natif n'est pas inclus.

## Lire un échec

Dans les logs, ouvre le job `CI monorepo`, puis l'étape rouge. Cherche d'abord la première ligne `error`, le nom du test/typecheck ou la commande qui s'est terminée avec un code différent de zéro. Les étapes vertes précédentes ont réussi; les suivantes n'ont généralement pas été lancées. Corrige le problème, puis pousse un nouveau commit ou mets à jour la Pull Request pour démarrer une nouvelle exécution.

## Trouver les résultats

Dans le dépôt GitHub, ouvre l'onglet **Actions**, puis choisis le workflow **CI** et une exécution. La page montre le commit ou la Pull Request qui l'a déclenchée, son résultat, sa durée et les logs par étape. Le même résultat apparaît aussi dans les contrôles de la Pull Request. La documentation GitHub décrit la [syntaxe des workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

## Rendre la CI obligatoire avant une fusion

Après une première exécution réussie, un administrateur du dépôt peut ouvrir **Settings → Branches** et ajouter une règle pour `modernization` ou `main`. Active **Require status checks to pass before merging**, puis sélectionne le contrôle `CI monorepo` dans la liste. Enregistre la règle et répète l'opération pour l'autre branche si les deux doivent être protégées. GitHub ne peut proposer le contrôle qu'après l'avoir vu dans une exécution.

La règle peut aussi demander que la branche de la Pull Request soit à jour avec sa branche cible avant la fusion. Consulte la documentation GitHub sur la [protection des branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) et les [contrôles de statut requis](https://docs.github.com/en/pull-requests/reference/status-checks).

## Validation de M2.3

`npm ci` a installé 639 paquets (644 audités). Avec Node 26.8.2 et npm 11.19.1, les 16 tests, les typechecks moteur/web/mobile et le build web ont réussi dans l'ordre prévu. Le YAML a été analysé avec le parseur déjà présent dans le dépôt; branches de déclenchement, permission en lecture seule et huit étapes ont été vérifiées. Aucun fichier de gameplay, dépendance ou lockfile n'a été changé.

La CI n'a pas encore été exécutée sur un runner GitHub. Le push de `chore/m2-ci` a échoué, car cette machine n'a pas de clé SSH utilisable (`Permission denied (publickey)`) et ne résout pas `github.com` en HTTPS. Après avoir poussé la branche avec un accès autorisé, ouvrir une Pull Request vers `modernization`; son premier contrôle hébergé vérifiera le workflow réel.

Commandes à exécuter depuis la racine après rétablissement de l'accès GitHub :

```sh
git push --set-upstream origin chore/m2-ci
gh pr create --repo Ayota-Daniel/MathPrime --base modernization --head chore/m2-ci --title "M2.3 : première CI GitHub Actions" --body "Ajoute une CI GitHub Actions minimale sur les PR et pushs vers modernization et main. Les tests du moteur, trois typechecks et le build web passent localement après npm ci. Le workflow GitHub reste à valider sur son premier runner hébergé."
```
